# ADR-0003: SPAKE2 (RFC 9382, P-256, asymmetric), implemented on filippo.io/nistec

- **Status:** Accepted, 2026-10-16. Revised after the adversarial review (this file was
  rewritten).
- **Evidence:** `docs/research/crypto.md`, https://www.rfc-editor.org/rfc/rfc9382.html

## Context
Two strangers share a short, low-entropy code (24 bits of secret words, ADR-0008). Used
directly as a key, it falls to offline brute force: anyone who recorded the traffic tries all
16.7M codes. A **PAKE** (password-authenticated key exchange) fixes this:
- a passive observer learns nothing;
- an active attacker gets exactly **one online guess** per run.

## Options
| Option | For | Against |
|---|---|---|
| **SPAKE2, RFC 9382** | A published RFC; **official P-256 test vectors**; specified key confirmation | No maintained Go library |
| CPace | Cleaner modern design | Still a draft (cpace-21); the only Go library is a 2021 "weekend project" |
| OPAQUE (RFC 9807) | Strong | Client/server with registration, the wrong shape for two peers |
| croc's `schollz/pake` | Ready-made | Non-standard curve; no key confirmation; croc v8 had a PAKE brute-force bug |
| Hash the code into a key (PBKDF2) | Trivial | **Broken.** Offline brute force of 24 bits takes seconds |

## Decision
Implement RFC 9382, suite **P256-SHA256-HKDF-HMAC**, in the **asymmetric** form, using
`filippo.io/nistec` (v0.0.4) for the elliptic-curve point arithmetic.

- **Roles are fixed.** The **sender is A** (uses M) and the **receiver is B** (uses N).
  - Use the RFC §6 constants for M and N (compressed SEC1 points).
  - Identities: A = `"p2p/1 send"`, B = `"p2p/1 recv"`. In DHT mode (Phase 5) A also
    includes the sender's ephemeral public key, so a forged rendezvous record fails
    confirmation (ADR-0008). These identities aren't in the RFC vectors, so the vector tests
    use the RFC's identities, and the same code path is used for both.
  - Why not symmetric? The RFC defines the symmetric variant (M=N) only through
    `hash_to_curve` (RFC 9380). nistec doesn't implement that, the RFC's test vectors don't
    cover it, and its transcript order is ambiguous when roles are symmetric. Our roles are
    known, so asymmetric is both correct and testable.
- **The secret `w`:** `w = SHA-512(len‖"p2p/1" ‖ len‖nameplate ‖ len‖words) mod n`, where `n`
  is the **group order** (which the RFC calls `p`).
  - Each field is length-prefixed, so field boundaries can't be shifted.
  - The 512-bit hash satisfies the RFC's "64 bits longer than the order" rule against bias.
- **Associated data (AAD):** the protocol version string. It goes into the confirmation-key
  derivation (RFC §4), so a downgrade fails confirmation.
- **Input checks:**
  - reject any received point that isn't a valid point on the curve;
  - reject the identity point;
  - reject `pA == pB` (no reflecting our own message back).
- **Key confirmation, RFC §3.3:**
  - A sends `cA = MAC(KcA, TT)`, and B replies with `cB = MAC(KcB, TT)`;
  - MACs are compared in constant time;
  - **no application data, metadata or address candidates are sent before both MACs
    verify;**
  - on a failure both sides abort and the nameplate is burned.
- **Tests:**
  - **All four RFC Appendix B test vectors**, reproduced byte for byte;
  - round trips with the right code and with a wrong code;
  - fuzzing on point decoding.

## Why no memory-hard function (argon2)?
The RFC says `w` SHOULD go through a memory-hard function, to slow offline guessing when a
transcript and a stored verifier both leak.
- We store no verifier.
- A passive transcript gives no offline guessing.
- An active attacker gets one online guess and nothing more.

So argon2 would add latency and protect nothing. This deviation is deliberate. (The review
confirmed this reasoning.)

## Consequences
- About 200 lines of security-critical code, the best learning in the project. The RFC's test
  vectors are the safety net.
- **No interoperability with magic-wormhole.** It uses a pre-RFC SPAKE2 on Ed25519.
- If CPace becomes an RFC with a solid Go library, revisit this decision.

## What an interviewer might ask
- *Why not hash the code?*
  - A 24-bit space falls to offline brute force in seconds.
  - A PAKE turns the attack into one online guess per run.
- *Isn't implementing crypto yourself dangerous?*
  - We implement a protocol from an RFC, not new primitives.
  - The curve arithmetic comes from a vetted library.
  - Our output matches the RFC's test vectors exactly.
- *Why reject pA == pB?* Otherwise an attacker can bounce A's own message back to A. A then
  runs both sides of the exchange against itself.
- *Why reduce mod the group order and not the field prime?* Scalars live in the group order.
  Reducing by the wrong modulus biases `w`, or produces scalars that aren't valid.
